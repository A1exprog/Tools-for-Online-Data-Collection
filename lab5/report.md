# Лабораторная работа №5. Вариант 4

## 1. Цель и вариант
* Вариант 4: quotes.toscrape.com — обход по тегам.
* Уровень 1 — список тегов на главной; уровень 2 — цитаты каждого тега + данные автора.
* Цель: промышленный паук на Scrapy (пагинация, двухуровневый обход, cb_kwargs, errback,
  пайплайн из 4 звеньев, вежливость и предохранители, JOBDIR, HTTP-кэш), отчёт о качестве
  и сравнение с no-code реализацией в n8n.

> **Стенд.** Все замеры ниже сделаны на локальной копии сайта: это открытый исходный код
> quotes.toscrape.com (проект spidyquotes от Zyte) с теми же данными и вёрсткой. Адрес
> подставляется параметром `-a base_url=http://127.0.0.1:8800/`, по умолчанию паук ходит на
> https://quotes.toscrape.com/. Время прогона почти целиком определяется паузами
> DOWNLOAD_DELAY/AutoThrottle, поэтому на боевом сайте оно практически такое же; отличаются
> только сетевые задержки.

## 2. Карта источника
- Точка входа: https://quotes.toscrape.com/
- robots.txt: ответ 404 — ограничений нет; проверка всё равно выполняется (ROBOTSTXT_OBEY=True).
- Уровень 1: главная и её пагинация `/page/1..10/`. На каждой странице есть облако топ-10 тегов
  и теги внутри цитат.
```
# body
└─ .container
   └─ .row
      ├─ .col-md-8
      │  ├─ .quote … div.tags a.tag[href="/tag/<tag>/page/1/"]   ← теги цитат
      │  └─ nav ul.pager li.next a[href="/page/N/"]               ← пагинация главной
      └─ .col-md-4.tags-box
         └─ span.tag-item
            └─ a.tag[href="/tag/<tag>/"]                          ← топ-10 тегов
```
- Уровень 2: страницы тегов с пагинацией.
```
# body
└─ .container
   └─ .row
      └─ .col-md-8
         ├─ .quote
         │  ├─ span.text
         │  ├─ span
         │  │  ├─ small.author
         │  │  └─ a[href="/author/<slug>"]      ← без «/» на конце
         │  └─ .tags
         │     └─ a.tag
         └─ nav ul.pager li.next a[href="/tag/<tag>/page/N/"]
```
- Карточка автора `/author/<slug>/`.
```
# body
└─ .container
   └─ .author-details
      ├─ h3.author-title
      ├─ span.author-born-date        "March 14, 1879"
      ├─ span.author-born-location    "in Ulm, Germany"
      └─ .author-description
```
- Схема обхода.
```
https://quotes.toscrape.com/  (уровень 1, страницы 1..10 по li.next)
│   ├─ div.tags-box a.tag            → /tag/<tag>/            → приводится к /tag/<tag>/page/1/
│   └─ div.quote div.tags a.tag      → /tag/<tag>/page/1/
│
└─▶ /tag/<tag>/page/N/  (уровень 2, cb_kwargs: tag, page)
       ├─ div.quote → QuoteItem: quote, author, tags, source_tag, tag_page, author_url
       ├─ li.next a → /tag/<tag>/page/N+1/
       └─ small.author + a → /author/<slug>/  (один запрос на автора, повторы отсекает dupefilter)
              └─▶ AuthorItem: author, author_born_date, author_born_place, author_bio
```
Почему теги собираются и со страниц главной: облако на главной содержит только 10 тегов, а через
цитаты этих тегов достижимы лишь 99 из 137 тегов (190 пар «цитата × тег»). Обход 10 страниц
главной даёт ссылки на все 137 тегов и закрывает требование «≥ 10 страниц списка».

- Используемые селекторы (только CSS по классам и структуре, индексных XPath нет):

| Уровень | Селектор | Поле | Тип |
|---|---|---|---|
| 1 | `div.tags-box span.tag-item a.tag` (текст, href) | source_tag, tag_url | str, URL |
| 1 | `div.quote div.tags a.tag` (текст, href) | source_tag, tag_url | str, URL |
| 1, 2 | `li.next a::attr(href)` | следующая страница | URL |
| 2 | `span.text::text` | quote | str |
| 2 | `small.author::text` | author | str |
| 2 | `div.tags a.tag::text` | tags | list[str] |
| 2 | `small.author + a::attr(href)` | author_url | URL |
| автор | `h3.author-title::text` | author | str |
| автор | `span.author-born-date::text` | author_born_date | date → ISO |
| автор | `span.author-born-location::text` | author_born_place | str |
| автор | `div.author-description::text` | author_bio | str |

Устойчивость к отсутствию полей: все поля берутся через `.get()` (при отсутствии — `None`, без
исключения), неполная запись не роняет паука, а отбраковывается в ValidatePipeline со счётчиком.

## 3. Архитектура Scrapy
- Проект создан `scrapy startproject lab5_quotes`: `items.py`, `pipelines.py`, `settings.py`,
  `spiders/tags.py`.
- **Spider, а не CrawlSpider.** Правила CrawlSpider (`Rule` + `LinkExtractor`) удобны, когда
  ссылки обходятся единообразно. Здесь каждому запросу нужно передать контекст через `cb_kwargs`
  (тег уровня 1, номер страницы тега), а теги из двух источников приводятся к одному URL.
  В обычном Spider это явно видно в коде и проще отлаживается.
- **Схема записи** (`items.py`):
  - `QuoteItem` — цитата в выдаче тега: quote, author, tags, source_tag, tag_page, author_url,
    business_key;
  - `AuthorItem` — карточка автора: author, author_url, born_date, born_place, bio, business_key.

  Цитата и автор хранятся раздельно и связываются по `author_url`. Итоговая запись варианта
  «цитата тега + данные автора» — представление `quotes_full` в БД.
- **Почему два Item, а не один.** Если склеивать цитату с автором прямо в пауке, приходится
  держать в памяти «цитаты, ждущие автора». При возобновлении через JOBDIR эта память теряется,
  а повторный запрос к автору отсекает dupefilter, поэтому часть записей пропадает. С двумя
  Item паук не хранит состояния: всё нужное для продолжения лежит в очереди запросов JOBDIR.
  Это подтверждено замером (раздел 6).
- **cb_kwargs:** `parse(list_page)`, `parse_tag(tag, page)`, `parse_author(author_url)`.
- **errback:** один на все запросы. Считает ошибки по типам: `errback/total`, `errback/http_<код>`,
  `errback/dns`, `errback/timeout`, `errback/<Исключение>`.
- **closed():** сохраняет полную статистику в `data/stats_<номер прогона>.json`. Номер прогона
  — следующий после максимального в `data/`. В файл добавляются причина остановки, длительность,
  base_url и снимок ключевых настроек (в том числе CLOSESPIDER_ITEMCOUNT).
- **Нормализация URL:**
  - `/tag/love/` и `/tag/love/page/1/` приводятся к одному виду, чтобы повтор отсёк dupefilter;
  - к ссылке на автора добавляется «/». Без этого каждый запрос автора получал редирект 308:
    лишний запрос и трафик, в черновом прогоне 45 из 196 ответов были такими.

## 4. Пайплайн и счётчики
| Порядок | Звено | Что делает | Счётчики (основной прогон) |
|---|---|---|---|
| 100 | ValidatePipeline | Обязательные поля. Цитата: quote, author, source_tag, author_url. Автор: author, author_url, дата, место, био. Иначе DropItem | `validate/passed/quote` 232, `validate/passed/author` 49, `dropped/missing_fields` 0 (+ разбивка `dropped/missing_fields/<тип>/<поле>`) |
| 200 | CleanPipeline | Схлопывание пробелов; снятие кавычек «“ ”» у цитаты; теги в нижнем регистре, отсортированы, без повторов; tag_page → int; дата `March 14, 1879` → `1879-03-14`, некорректная → DropItem; «in » в месте рождения убирается; построение business_key | `clean/quotes` 232, `clean/authors` 49, `clean/dates_to_iso` 49, `dropped/invalid_date` 0 |
| 300 | DuplicateFilterPipeline | Дедупликация по бизнес-ключу, не по URL. Цитата: `автор\|цитата\|тег`; автор: имя | `dropped/duplicates` 0 |
| 400 | SQLitePipeline | Соединение в open_spider/close_spider, пакеты по 50 (`executemany`), `INSERT OR REPLACE`, две таблицы + представление | `pipeline/sqlite_written` 281 (232 + 49), `pipeline/sqlite_batches` 6 |

Схема БД `data/crawl.db`:
- `quotes(business_key PK, quote, author, tags, source_tag, tag_page, author_url, scraped_at)`;
- `authors(author_url PK, business_key UNIQUE, author, author_born_date, author_born_place,
  author_bio, scraped_at)`;
- индексы по `quotes.author_url` и `quotes.source_tag`;
- представление `quotes_full` = quotes LEFT JOIN authors.

Повторный прогон не создаёт дублей, потому что ключ — PRIMARY KEY и используется INSERT OR REPLACE.

Почему в бизнес-ключе цитаты есть тег. Одна цитата в среднем стоит на 2,4 тегах. По условию
варианта запись — «цитата тега», поэтому ключ — пара автор + цитата в разрезе тега. Если нужна
пара автор + цитата без тега, это `SELECT DISTINCT author, quote FROM quotes`: 97 строк.

## 6. JOBDIR и HTTPCACHE
**JOBDIR.** Прогон `-s JOBDIR=jobstate/tags_run1` был прерван через 60 с (SIGINT, мягкая
остановка), затем запущен повторно той же командой. Для чистоты опыта использовалась отдельная
БД `data/jobdir_demo.db`.

| Прогон | close_reason | Записей | Запросов | dupefilter/filtered | Очередь на диске | Время |
|---|---|---:|---:|---:|---|---:|
| №2 (прерван) | shutdown | 71 | 67 | 121 | enqueued/disk 108, dequeued/disk 66 | 80 с |
| №3 (возобновлён, «Resuming crawl (42 requests scheduled)») | finished | 210 | 137 | 298 | dequeued/disk 136 | 165 с |
| **Итого** | | **281** | 204 | | | 245 с |

Итог: 71 + 210 = 281 запись, ровно как в непрерывном прогоне. В `jobdir_demo.db` 232 цитаты
и 49 авторов, у всех цитат есть данные автора. Ни одна страница не скачана повторно:
- 202 страницы в двух частях;
- плюс 2 запроса robots.txt, по одному на каждый запуск.

Уже пройденные URL отсёк dupefilter по сохранённому `requests.seen`.

**HTTPCACHE.** Два прогона подряд с `-s HTTPCACHE_ENABLED=True`, БД `data/cache_demo.db`:

| Прогон | httpcache/store | httpcache/hit | httpcache/miss | Время |
|---|---:|---:|---:|---:|
| №4 (холодный кэш) | 202 | 0 | 202 | 244 с |
| №5 (тёплый кэш) | 0 | 202 | 0 | **2,4 с** |

С тёплым кэшем к сайту не уходит ни одного запроса. Ответы отдаются из `.scrapy/httpcache/` раньше
очереди загрузчика, поэтому паузы DOWNLOAD_DELAY не действуют и прогон в ~100 раз быстрее.
Так удобно отлаживать селекторы и пайплайн, не нагружая сайт.

## 9. Smoke-check и риски редизайна
`quality/smoke_check.py` запускается после прогона и сравнивает БД с эталоном
`data/quality_summary.json`. Код выхода 1 означает FAIL, это удобно для cron или n8n.

Правила:
- число записей упало более чем на 20 % → FAIL;
- пустые обязательные поля более чем в 5 % записей → FAIL;
- эталон обновляется только после успешной проверки.

Проверка на реальной БД: OK (232 записи, пустых 0 %). Имитация сбоя на копии БД (удалено 30 %
цитат, у 5 авторов пустая биография, `SMOKE_DB=…`):

```
FAIL: число записей упало более чем на 20%: 232 → 161
FAIL: пустые обязательные поля в 16.2% записей (> 5%): {'author_bio': 26}
Эталон не обновлён.        (exit=1)
```

Что сломается при редизайне сайта и как это заметить:

| Изменение вёрстки | Последствие | Чем ловится |
|---|---|---|
| Переименован класс `quote`/`text`/`author` | 0 цитат со страниц тегов | smoke-check: падение > 20 %; `pages/tag` есть, а `clean/quotes` = 0 |
| Убрана ссылка `(about)` у автора | нет author_url | `dropped/missing_fields/quote/author_url` |
| Новый формат даты рождения | автор отброшен | `dropped/invalid_date`, пустые поля автора в `quotes_full` → smoke-check > 5 % |
| Пагинация на JS / другой класс `next` | только первая страница тегов | падение записей > 20 % |
| Облако тегов убрано | теги всё равно находятся через страницы главной (два источника) | `tags/found_via_top10` = 0 |
| Блокировка / 429 / 5xx | повторы, затем errback | `retry/count`, `errback/http_<код>`, CLOSESPIDER_ERRORCOUNT |

## 11. Выводы
- **(а) Разовый обход 500 страниц — Scrapy.** Готовый паук пройдёт их примерно за 8–10 минут
  при тех же паузах. Повторные ссылки отсекаются автоматически: в n8n на 86 цитат ушло 86
  запросов авторов вместо 43. При обрыве прогон можно продолжить. В n8n все элементы живут
  в памяти одного выполнения, а сбой на 400-й странице означает повтор с нуля.
- **(б) Ежедневный обход 40 000 страниц — Scrapy** (+ Scrapyd/cron). Нужны JOBDIR,
  AutoThrottle, предохранители, пакетная запись в БД и статистика для контроля деградации.
  n8n на таком объёме упирается в память и скорость выполнения узлов.
- **(в) Сотня страниц + отчёт в мессенджер — n8n.** Объём маленький, расписание и отправка
  в Telegram делаются узлами без кода, а ветка ошибок сразу сообщает о сбое.
- **Гибридный контур.** n8n по расписанию запускает Scrapy (Execute Command / Scrapyd API),
  затем `smoke_check.py`, по коду выхода выбирает ветку и отправляет в мессенджер сводку из
  `stats_<N>.json` и БД.

## 12. Правовая и этическая оценка
- **robots.txt:** ROBOTSTXT_OBEY=True. У quotes.toscrape.com robots.txt отсутствует (404),
  ограничений на обход нет. Сайт создан Zyte специально для обучения скрапингу.
- **Нагрузка:**
  - не больше 4 параллельных запросов на домен, на практике ~0,8 запроса/с;
  - пауза 1 с с разбросом, AutoThrottle;
  - повторы только для временных ошибок;
  - отладка через HTTP-кэш, без повторных обращений к сайту;
  - User-Agent с контактом.
- **Обход защит:** капча, антибот и авторизация не обходятся. Страница логина сайта не
  используется.
- **Персональные данные (152-ФЗ).** Собираются имя автора, дата и место рождения, биография.
  Формально это сведения о физических лицах, но все авторы — известные, большей частью
  умершие публичные персоны. Данные уже опубликованы на сайте и используются в учебных целях.
  Данные пользователей, контакты и идентификаторы живых частных лиц не собираются. При
  переносе подхода на реальные сайты с ПДн нужны:
  - правовое основание обработки;
  - минимизация полей;
  - сроки хранения;
  - запрет на распространение без согласия (ст. 6, 7, 10.1 152-ФЗ).
- **Авторское право:** цитаты — короткие фрагменты произведений. Используются для учебного
  анализа, датасет не публикуется и не распространяется.
