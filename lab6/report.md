# Лабораторная работа №6. Хранение, очистка и структурирование данных

**Вариант 4 — погода и наблюдения.** Целевая схема:
- наблюдение — локация, отметка времени UTC, показатели;
- справочник локаций.

Все цифры получены прогоном 02.11.2026: `python src/collect.py` → `python run_all.py` (результаты — `clean/`, `db/`, `mart/`, `quality_report.ipynb`).

## 1. Цель и источники

Цель — построить слой хранения и качества: трёхслойное хранилище raw → clean → mart, очистку с протоколом, контракт данных, идемпотентную загрузку в БД с историей и метрики качества со «светофором».

| | Источник 1 — HTML | Источник 2 — API |
|---|---|---|
| Что | справочник городов России с координатами | суточная погода: максимум и минимум температуры, осадки |
| Где | https://time-in.ru/coordinates/russia | NASA POWER, `power.larc.nasa.gov/api/temporal/daily/point` (основной по плану — Open-Meteo, см. ниже) |
| Формат | HTML-список `ul.coordinates-items`, координаты строкой «55.75, 37.62» | JSON, значения по датам `YYYYMMDD`, пропуск = −999 |
| Объём | 343 города за запуск | 25 городов × 30 суток = 750 наблюдений (27.09–26.10.2026) |
| Чем различаются | текст «как на странице», русские названия, координаты строкой | числа, даты без таймзоны, маркер пропуска −999, координаты берутся из справочника |

Связь источников: город из справочника → `location_id` → наблюдения. В API передаются координаты из HTML-справочника, а согласованность источников проверяется бизнес-правилом и метрикой.

**Отказ основного API.** По плану API-источник — архив Open-Meteo. В день сбора оба его эндпоинта отвечали `503 {"reason":"The service is overloaded"}`: и `archive-api`, и `api.open-meteo.com` с `past_days`, на все попытки с паузами 5–20 с. Это перегрузка самого сервиса, о ней пишут и другие пользователи ([GitHub](https://github.com/onpaj/Anela.Heblo/issues/4513)). Сборщик в таком случае автоматически переходит на резервный источник с теми же показателями — NASA POWER. Поэтому все 750 наблюдений в сыром слое имеют `_source = "nasa-power"`.

В коде и протоколе слот API-источника по-прежнему называется `open-meteo` (`RAW_FILES`, колонка `source` протокола), а реальный источник каждой записи — в поле `source`. Задержка публикации у NASA POWER около недели, поэтому окно дат сдвинуто: 30 суток, заканчивая 7 днями назад.

```

                                                            │
                                                            ▼

```

**Сырой слой.**
- Файлы открываются только в режиме дозаписи (`append_jsonl`, режим `"a"`). Существующие строки не меняются.
- У каждой записи есть служебные поля `_source`, `_source_url`, `_collected_at` (UTC, ISO 8601 с `+00:00`), `_parser_version`, `_status` и `_run_id`.
- Для HTML значения сохранены «как на странице»: `city_raw`, `city_href_raw`, `coords_raw` («55.75, 37.62»), `latitude_raw`, `longitude_raw` (строки).

Справочник собран 5 раз (5 разных `_run_id`, 1 715 строк): `collect.py` пришлось перезапускать, пока искали обход отказа Open-Meteo. Все копии остались в сыром слое и убраны на шаге дубликатов (раздел 4).

**Пересборка clean из raw без обращения к сайтам.** `src/rebuild.py` удаляет `clean/` и строит его заново только из `raw/*.jsonl`. `run_all.py` запускает пересборку два раза подряд и сравнивает контрольные суммы (`clean/rebuild_check.json`):

## 3. Сравнение форматов

Один и тот же чистый набор (750 строк) сохранён в трёх форматах. Время — медиана 7 чтений (`clean/format_benchmark.csv`).

| Формат | Размер, КБ | Полное чтение, мс | Чтение 3 столбцов, мс | Дата после чтения | `day_code` («0927») после чтения | `precipitation_sum` |
|---|---:|---:|---:|---|---|---|
| CSV | 237,9 | 3,46 | 2,91 | `object` (строка) | **int64 927** — ведущий ноль потерян | float64 |
| JSON Lines | 409,1 | 7,00 | 7,33 | `object` (строка `…T00:00:00.000Z`) | **int64 927** — ведущий ноль потерян | float64 |
| Parquet | **25,9** | **1,71** | **1,26** | `datetime64[ns, UTC]` | `'0927'` — строка сохранена | `Float64` (nullable) |

**Выводы:**
- **Parquet — для clean и mart.** Он в 9 раз меньше CSV и в 16 раз меньше JSONL, быстрее читается и умеет читать отдельные столбцы. Типы сохраняются: дата остаётся датой с таймзоной UTC, строка с ведущим нулём — строкой, целые и дробные с пропусками — nullable-типами.
- **JSON Lines — для raw.** Формат допускает дозапись по строке и разные наборы полей у разных источников, а сырые значения хранит без приведения типов. Именно поэтому из него можно перепарсить данные.
- **CSV — только для обмена** (выгрузка `nocode_result.csv` из n8n). Как хранилище он не годится: типы теряются, `day_code` превращается в число 927.

## 5. Контракт данных (pydantic v2)

`src/contract.py` содержит две модели.

**`Location`:**
- типы и ограничения: `min_length`, `max_length`, `ge` и `le` для координат, шаблон URL;
- валидатор `slug_format`: ключ должен быть ASCII-slug;
- валидатор `utc_only`: дата сбора только в UTC.

**`Observation`:**
- ограничения: `gt=-90, le=60` для температур, `ge=0, le=500` для осадок, шаблон `day_code` `^(0[1-9]|1[0-2])(…)$`;
- 3 собственных валидатора: `utc_only` (даты только с UTC), `slug_format`, `no_tracking` (в URL нет `utm_`);
- `model_validator` с 4 проверками согласованности:
  - tmax ≥ tmin;
  - `observation_id` = `location_id` + `_` + дата;
  - `day_code` соответствует дате;
  - дата сбора не раньше даты наблюдения.

Невалидные записи попадают в `rejects` с полем и причиной (`validate_rows`).

Проверка на заведомо битых записях (`contract.demo_broken()`). Каждая запись нарушает ровно одно правило:

| Проверка | Результат | Поле | Сообщение |
|---|---|---|---|
| эталонная запись | принята | — | — |
| широта вне диапазона (`Field le=90`) | отбракована | latitude | Input should be less than or equal to 90 |
| наивная дата без таймзоны (`utc_only`) | отбракована | observation_time_utc | наивная дата без таймзоны; ожидается UTC |
| кириллический ключ (`slug_format`) | отбракована | location_id | location_id должен быть ASCII-slug |
| utm-метки в URL (`no_tracking`) | отбракована | source_url | URL содержит метки трекинга utm_* |
| осадки < 0 (`Field ge=0`) | отбракована | precipitation_sum | Input should be greater than or equal to 0 |
| пустой город (`min_length=2`) | отбракована | city | String should have at least 2 characters |
| `day_code` без ведущего нуля (pattern) | отбракована | day_code | String should match pattern … |
| tmax < tmin (`model_validator`) | отбракована | model | temperature_2m_max < temperature_2m_min |
| ключ не совпадает с датой (`model_validator`) | отбракована | model | observation_id ≠ location_id + '_' + дата |
| сбор раньше наблюдения (`model_validator`) | отбракована | model | данные собраны раньше даты наблюдения |

В реальном прогоне контракт отказов не дал (0 из 750 и 0 из 340). Все нарушения поймала очистка раньше, а контракт остался последней линией защиты перед БД.

## 6. Схема БД

`db/schema.sql` (SQLite). Все даты хранятся как TEXT в ISO 8601 с явным `+00:00`, это проверяется через CHECK.

| Таблица | Ключ | Ограничения | Назначение |
|---|---|---|---|
| `locations` | PK `location_id` — бизнес-ключ (slug), не URL | NOT NULL; CHECK на формат slug, длину названия, диапазоны координат, `+00:00`; UNIQUE (широта, долгота, город) | справочник |
| `observations` | PK `observation_id` = локация + дата | FK → `locations`; NOT NULL на температуры; CHECK tmax ≥ tmin, диапазоны, осадки `NULL или 0–500`, `length(day_code)=4`; UNIQUE (`location_id`, `observation_time_utc`) | наблюдения |
| `observations_history` | PK (`observation_id`, `valid_from`) | частичный UNIQUE-индекс «одна актуальная версия» (`WHERE is_current = 1`), CHECK `valid_to > valid_from` | SCD Type 2 |
| `rejects` | автоинкремент | `payload` — валидный JSON (CHECK `json_valid`); UNIQUE (хэш payload, шаг) — повторная загрузка не плодит дубли | отбракованные записи |
| `load_runs`, `quality_runs` | время прогона | CHECK на вердикт | журналы загрузки и качества |

**Служебные поля** в `locations` и `observations`: `source`, `source_url`, `parser_version`, `collected_at`, `updated_at`.

**Индексы под фактические запросы:**
- `idx_obs_time` по `observation_time_utc` — для динамики по дням;
- UNIQUE (`location_id`, `observation_time_utc`) — заодно служит индексом для выборок по городу и периоду;
- `idx_rejects_reason` — для разбора отказов.

**SQL-представления mart:** `v_city_stats`, `v_daily_dynamics`, `v_top_warmest`.

**Почему SCD2, а не снапшоты.** Архивные значения меняются редко: реанализ уточняется задним числом. Ежедневные снапшоты копировали бы все 750 строк при каждом прогоне. SCD2 хранит только изменения и даёт запрос «состояние на любую дату», это задание на дополнительные баллы. Версии создают триггеры `trg_obs_insert` и `trg_obs_update`, поэтому история ведётся при любой загрузке, в том числе пакетной.

## 7. Идемпотентность и история изменений

Загрузка устроена так:
- пакеты по 200 строк через `executemany`;
- `INSERT … ON CONFLICT (observation_id) DO UPDATE … WHERE` значения изменились;
- поэтому повторная загрузка тех же данных не трогает `updated_at`.

Три прогона на отдельной БД `db/idempotency_demo.db` (`python db/load.py --demo`):

| Прогон | На входе | Вставлено | Обновлено | Без изменений | Строк в таблице | Версий в истории |
|---|---:|---:|---:|---:|---:|---:|
| 1. Исходный | 750 | 750 | 0 | 0 | 750 | 750 |
| 2. Повторный, те же данные | 750 | 0 | 0 | 750 | 750 | 750 |
| 3. Изменены две записи | 750 | 0 | **2** | 748 | 750 | **752** |

- Во втором прогоне `updated_at` остался прежним у 750 строк из 750.
- В третьем прогоне изменены `abakan_2026-09-27` (tmax 9,64 → 11,1) и `armavir_2026-10-12` (осадки 0,0 → 2,4). Обновились только эти две строки.

История (SCD2) по изменённым записям:

| observation_id | valid_from | valid_to | is_current | tmax | осадки |
|---|---|---|---:|---:|---:|
| abakan_2026-09-27 | 15:33:45.746 | 15:33:45.778 | 0 | 9,64 | 2,65 |
| abakan_2026-09-27 | 15:33:45.778 | — | 1 | **11,10** | 2,65 |
| armavir_2026-10-12 | 15:33:45.746 | 15:33:45.778 | 0 | 25,80 | 0,00 |
| armavir_2026-10-12 | 15:33:45.778 | — | 1 | 25,80 | **2,40** |

Запрос «состояние на дату» для момента второго прогона возвращает `abakan_2026-09-27`: tmax 9,64 (тогда), а текущее значение — 11,1.

В рабочей БД `db/warehouse.db` два прогона загрузки: первый вставил 750 строк, второй (повторный `run_all.py`) — 0 вставок, 0 обновлений, 750 без изменений.

**Проверка ограничений** — каждая попытка отвергнута БД:

| Попытка | Сообщение SQLite |
|---|---|
| дубликат первичного ключа (обычный INSERT) | UNIQUE constraint failed: observations.observation_id |
| tmax < tmin | CHECK constraint failed: temperature_2m_max >= temperature_2m_min |
| осадки < 0 | CHECK constraint failed: precipitation_sum IS NULL OR precipitation_sum BETWEEN 0 AND 500 |
| дата без таймзоны | CHECK constraint failed: observation_time_utc LIKE '%+00:00' |
| нет температуры | NOT NULL constraint failed: observations.temperature_2m_max |
| неизвестная локация | FOREIGN KEY constraint failed |
| второй замер города за те же сутки | UNIQUE constraint failed: observations.location_id, observations.observation_time_utc |

## 8. Метрики качества и светофор

`src/quality.py`: 10 метрик, пороги «зелёный / жёлтый» (хуже жёлтого — красный), итоговый вердикт по худшей метрике. Результаты пишутся в `clean/quality_metrics.csv` и таблицу `quality_runs`.

| Метрика | Значение | Зелёный | Жёлтый | Статус | Обоснование порога |
|---|---:|---|---|---|---|
| Полнота обязательных полей (8 полей) | 100 % | ≥ 99 | ≥ 95 | green | без обязательных полей запись бесполезна |
| Полнота необязательного поля (осадки) | 100 % | ≥ 95 | ≥ 80 | green | осадки нужны для mart, но пропуск допустим (NULL) |
| Уникальность ключа `observation_id` | 100 % | = 100 | ≥ 99,5 | green | дубль ключа ломает UPSERT и агрегаты |

**Итоговый вердикт — жёлтый**, загрузка в mart разрешена. Жёлтый статус объясняется только синтетической порчей, которую мы внесли намеренно.

**Прерывание при красном статусе.** Функция `check_gate()` бросает `QualityGateError`, и `mart.py` не строит витрины. На реальных данных это уже сработало.
- В первом прогоне порог актуальности был рассчитан на Open-Meteo (задержка 1–2 суток). - После этого пороги стали считаться относительно обычной задержки источника (`EXPECTED_LAG`).
- Дополнительно в `quality_report.ipynb` на копии чистого слоя удаляется 40 % наблюдений. Валидность падает до 56 %, покрытие — до 60 %, объём — на 40 %. Все три метрики красные, шлюз прерывает загрузку.

## 9. Слой mart

**Представления** — одновременно SQL-view в БД и Parquet-файлы в `mart/views/`:

| Представление | Строк | Содержание |
|---|---:|---|
| `city_stats` | 25 | по каждому городу: дней, средние tmax и tmin, сумма осадков, дней с осадками |
| `daily_dynamics` | 30 | по каждым суткам (27.09–26.10): число городов, средние tmax, tmin и осадки |
| `top_warmest` | 10 | топ-10 городов по среднему суточному максимуму |

Топ-3 самых тёплых: Астрахань (21,8 °C), Анапа (21,7 °C), Армавир (21,3 °C). Больше всего осадков в Артёме (Приморье) — 134,4 мм за 30 суток. Средний максимум по 25 городам — 12,7 °C (от 1,6 до 21,8 °C).

**Партиционирование.** Снапшоты чистого слоя пишутся с разбиением по дате сбора: `mart/snapshots/dt=YYYY-MM-DD/` (`partition_cols=["dt"]`). Повторный прогон за ту же дату перезаписывает партицию. Сейчас есть партиция `dt=2026-11-02`, и её чтение одной партицией вернуло 750 строк по 25 городам. При ежедневном сборе рядом появляются новые партиции, и любой день читается отдельно.

**Графики:**
- `mart/temperature_charts.png` — распределение суточных температур и динамика средних tmax и tmin по дням;
- `mart/top_warmest.png` — топ-10 городов.

## 10. No-code (n8n)

Workflow `nocode/workflow.json` поднимается вместе с PostgreSQL через `nocode/docker-compose.yml`. Схема БД — `nocode/schema_postgres.sql`. Что делает workflow:
- читает `raw/locations_html*.jsonl` и `raw/weather_api*.jsonl`, то есть больше 30 записей;
- нормализует 5+ полей в узлах Code: NFKC, `\xa0`, транслит-ключ, числа с запятой, даты, utm-метки;
- сортирует по времени сбора и убирает дубли узлом Remove Duplicates по ключу, оставляя самую свежую запись;
- проверяет правила и через IF разделяет валидные и невалидные записи;
- загружает в Postgres через `INSERT … ON CONFLICT DO UPDATE … WHERE IS DISTINCT FROM` (UPSERT с обновлением только изменившихся строк); справочник загружается раньше наблюдений;
- пишет отказы в таблицу `rejects`, отказы самой БД тоже идут туда;
- выгружает `nocode/nocode_result.csv`;
- запускается по расписанию в 03:00.

| Этап пайплайна | В коде | В n8n | Что не удалось |
|---|---|---|---|
| Чтение raw | `read_jsonl` | Read Files + Extract From File + Code | — |
| Нормализация текста | `normalize_text` (NFKC, `\xa0`, zero-width) | Code (JS) | это уже код, а не no-code |
| Бизнес-ключ | транслит-slug, нормализация URL | Code (JS) | — |
| Типизация | Decimal/float, nullable-типы, даты UTC | JS `Number`, строки ISO | в JS нет Decimal и nullable-целых; NaN между узлами превращается в null — ошибки типизации пришлось переносить отдельным полем |
| Пропуски → отказ | шаг 4 с причиной | IF + ветка в `rejects` | — |
| Дубликаты | полные, по ключу, почти-дубли, свежая запись | Sort + Remove Duplicates | почти-дубли (координаты отличаются на < 0,01°) не распознаются |
| Бизнес-правила | 9 + 5 правил | Code + IF | правило «локация есть в справочнике» требует соединения двух веток; вместо него срабатывает FK в Postgres |
| Контракт pydantic | 2 модели, валидаторы, `model_validator` | — | **не переносится**: остаются ручные `if` в Code без типизированной модели |
| UPSERT | `ON CONFLICT DO UPDATE WHERE` | Postgres (Execute Query) с тем же SQL | — |
| История SCD2 | триггеры SQLite | — | n8n не создаёт триггеры; историю пришлось бы вести отдельным SQL в БД |
| Метрики и светофор | 10 метрик, пороги, `check_gate` | — | **плохо переносится**: считать можно только в Code, без истории прогонов |
| Parquet и партиции | pandas + pyarrow | — | n8n не работает с Parquet |
| Протокол очистки | `protocol.csv` по шагам | — | нет счётчиков «до/после» по шагам без дополнительного кода |

Слой качества данных в no-code почти целиком сводится к коду внутри узлов Code: контракт, метрики, история и протокол без кода не делаются.

## 11. Правовой раздел

- **Состав данных:** названия городов и координаты (открытый справочник), суточные метеопоказатели (открытые данные NASA). Сведений о физических лицах нет, персональные данные в смысле 152-ФЗ и GDPR не обрабатываются.
- **Правомерность сбора:**
  - robots.txt time-in.ru проверяется перед сбором через `RobotFileParser` по адресу `/robots.txt`, путь `/coordinates/russia` разрешён;
  - User-Agent честный, учебный, с контактом;
  - справочник — один запрос за запуск;
  - API — один пакетный запрос к Open-Meteo, при отказе по одному запросу на город к NASA POWER с паузой 1 с;
  - повторы — только для 429 и 5xx, с растущей паузой.
- **Условия использования API.** Open-Meteo бесплатен для некоммерческого использования. Данные NASA POWER открыты и требуют указать источник: «Data obtained from the NASA Langley Research Center POWER Project».
- **Место и срок хранения:** локально в папке проекта (`raw/`, `clean/`, `db/`, `mart/`), до защиты работы, затем удаление. Сырой слой не публикуется.
- **Минимизация:** сохраняются только поля, нужные для задачи.
- **Если бы данные содержали ПДн:**
  - понадобилось бы правовое основание по ст. 6 152-ФЗ или ст. 6 GDPR («общедоступность» сама по себе его не даёт — ст. 10.1 152-ФЗ);
  - минимизация (ст. 5 GDPR);
  - срок хранения и порядок удаления, обезличивание в clean;
  - запрет передачи третьим лицам без согласия.
